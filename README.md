## Why this exists

Every engineer has lost a week to an unfamiliar repository — reading files in a random order,
building a mental model that turns out to be wrong, asking questions that are already answered
somewhere in the source.

GitBrain reads the whole repository and hands you the model directly.

**The one design decision that matters:** everything GitBrain tells you is _computed from the
source_, not generated by a language model. The import graph is parsed. Cycles are found with
Tarjan's algorithm. Complexity is measured. Secrets are matched and entropy-checked. That makes
the output reproducible, checkable, and free.

A language model is optional, and it sits _on top_ of those facts — it explains them more
fluently, but it never invents them. **GitBrain works completely with zero API keys and zero
accounts.**

## Features

### Repository analysis

- Analyze any **public GitHub repository** by URL, or **upload a ZIP** of a local project
- Both paths run through **one ingestion pipeline** — no `git` binary, no temp directories, no
  filesystem at all, so it runs unchanged on serverless
- Skips dependencies, build output, binaries and lockfile bodies, and **reports what it skipped**
- Detects languages, frameworks, package managers, runtimes, CI, deployment targets, test
  frameworks, databases, architecture style and API style — **each with the evidence that
  produced it**

### The knowledge base

Eighteen documents generated from measured facts, each citing the files it drew from:

|                         |                     |                        |
| ----------------------- | ------------------- | ---------------------- |
| Executive summary       | Project purpose     | Folder explanation     |
| Architecture overview   | Dependency analysis | Code complexity        |
| Technical debt          | Entry points        | Data flow              |
| Authentication flow     | API overview        | Database overview      |
| Deployment guide        | Setup guide         | Environment variables  |
| Performance bottlenecks | Security risks      | Suggested improvements |

When a subsystem is absent, the document **says so plainly** and lists what was searched for.
It will not invent an authentication flow that does not exist.

### Interactive code graph

- Every resolved import across TypeScript, JavaScript, Python, Go, Rust, Ruby, PHP, Java, Kotlin
- **Circular dependency detection** via iterative Tarjan SCC (verified against a 5,000-node graph)
- Node size by lines of code, colour by language, cycles highlighted
- Filter by path, language or "cycles only"; layered and force-directed layouts
- Zoomable **treemap** of the repository by bytes
- Instability metric per module, with a plain explanation of what it means

### Search & chat

- **BM25 ranking** with symbol and path boosting, so `createUser` finds its _definition_ before
  its twenty call sites
- Morphological expansion, so "authentication" matches `auth`, `authenticate`, `authorize`
- Streaming chat with **clickable citations** into real files and line ranges
- Works with **no API key** via local retrieval; add OpenRouter for conversational depth

### Health & security

- Eight scored dimensions, each with a rationale made of **numbers you can check**
- Hard floors that cannot be gamed: zero tests caps the testing score at 10; a committed critical
  secret caps security at 20
- Entropy-gated secret detection across 22 rules, with placeholder and `.env.example` suppression,
  and **findings are always redacted**
- Dangerous-sink analysis, dependency flags, duplicate blocks, large files, undocumented env vars

## Architecture

```
src/
├── core/            Pure TypeScript. No React, no Next.js, no Node built-ins.
│   ├── ingest/      The one place allowed to touch the network. URL → ZIP → virtual FS.
│   ├── detect/      Languages, dependencies, stack, entry points.
│   ├── graph/       Import parsing, resolution, module graph, Tarjan SCC, file tree.
│   ├── metrics/     Complexity, duplication, technical debt.
│   ├── security/    Secret scanning, env vars, risk analysis.
│   ├── readme/      README scoring and section generation.
│   ├── health/      Eight-dimension scoring.
│   ├── knowledge/   The 18 generated documents.
│   ├── search/      Chunking, inverted index, BM25.
│   └── analyze.ts   The pipeline that composes all of the above.
├── lib/             Adapters: AI provider, storage, auth, rate limiting, env.
├── features/        Feature-first UI: analyze, report, graph, knowledge, search, chat.
├── components/      Design-system primitives and shared renderers.
└── app/             Next.js App Router routes and API handlers.
```

**`src/core` is framework-free, and ESLint enforces it** — it cannot import React, Next.js, or
Node built-ins. The whole analysis engine is portable to a CLI, a worker, or the browser, and is
unit-tested in isolation without a DOM.

### Adapters, not requirements

Every integration is optional and resolved at runtime:

| Capability | Configured                       | Not configured                                     |
| ---------- | -------------------------------- | -------------------------------------------------- |
| AI         | OpenRouter model answers         | Local retrieval over the real analysis             |
| Storage    | Supabase Postgres                | Bounded in-memory LRU                              |
| Auth       | Clerk accounts, private analyses | Anonymous, shareable by URL                        |
| GitHub     | 5,000 requests/hour              | 60 requests/hour (archives are never rate limited) |

## Installation

**Requirements:** Node.js ≥ 20.11 and pnpm.

```bash
git clone https://github.com/itsshreyasbhardwaj-design/gitbrain.git
cd gitbrain
pnpm install
pnpm dev
```

Open <http://localhost:3000>. That is the whole setup — **no `.env` file is required.**

To enable an optional integration:

```bash
cp .env.example .env.local
```

Every variable in `.env.example` is optional and documents exactly what it turns on.

## Usage

### Analyze a repository

Paste any public GitHub URL. All of these work:

```
https://github.com/honojs/hono
github.com/honojs/hono
honojs/hono
https://github.com/honojs/hono/tree/next
git@github.com:honojs/hono.git
```

Or drop a `.zip` anywhere on the input panel to analyze a local project. Nothing is sent to a
third party.

### Ask the codebase

```
Where is authentication implemented?
What starts the application?
How do I run this locally?
Explain the data flow
What are the biggest risks in this codebase?
```

Answers stream, cite real files, and the citations are clickable.

### Scripts

```bash
pnpm dev              # Development server
pnpm build            # Production build
pnpm test             # Unit + integration tests
pnpm test:coverage    # With coverage thresholds
pnpm test:e2e         # Playwright, against a real production build
pnpm typecheck        # tsc --noEmit
pnpm lint             # ESLint
pnpm verify           # typecheck + lint + test + build
```

## Testing

697 tests across three layers:

- **Unit** — colocated with each analyzer. Every heuristic has a fixture proving what it does
  _and_ what it deliberately refuses to do.
- **Integration** — `tests/integration/self-analysis.test.ts` runs the entire pipeline over
  GitBrain's own source and asserts on the result. It has caught bugs unit tests structurally
  could not: a crash on identifiers named `constructor`, and a secret scanner that flagged its
  own test fixtures at critical severity.
- **End-to-end** — Playwright against a real production build, including a mobile viewport pass
  and API contract tests covering the SSRF boundary.

```bash
pnpm verify
```

## Deployment

Deploys to Vercel with no configuration:

[![Deploy with Vercel](https://vercel.com/button)](https://vercel.com/new/clone?repository-url=https://github.com/itsshreyasbhardwaj-design/gitbrain)

It also runs anywhere Node 20+ runs:

```bash
pnpm build && pnpm start
```

For durable, shared storage, apply `supabase/migrations/0001_init.sql` and set the Supabase
variables. That schema enables `pgvector` and ships an unused `analysis_chunks` table as the seam
for hybrid retrieval — lexical BM25 stays, because exact identifier matching is a feature, not a
limitation.
